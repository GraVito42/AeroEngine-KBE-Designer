## **Knowledge Based Engineering (KBE)** 

## _**What is it? A methodology? A technology?**_ 

Knowledge Based Engineering ( **KBE** ) is a **methodology** that formalizes, captures, and reuses engineering knowledge to automate and support design and analysis processes. 

It is implemented through specific **computational technologies** , referred to as KBE systems, which enable the formalization and capture of, among others: 

- Design intent 

- Decision logic 

- Parametric relations 

- Constraints and rules 

- Best practices and heuristics 

- Process knowledge (including but not limited to geometry manipulation)

> **Knowledge Based Engineering (KBE)** _**How does KBE manifest? What does it do in practice?**_ 

KBE manifests through the generation of **domain-specific** software applications ( **KBE apps** ) that use **explicitly encoded** engineering knowledge to automate and support design and analysis tasks. Key benefit of KBE applications: 

- Automation of repetitive and rule-based design tasks 

- • Multidisciplinary integration in all phases of the design process 

- • Formalization and preservation of valuable domain specific knowledge for re-use

When facts are missing, the expert asks the customer to help. If facts to prove the hypothesis cannot be found, the expert will switch to a different hypothesis and start all over.

## **Frame Based Systems** 

A **Class-frame** is used as template to define **a type of objects** E.g. the class-frame Aircraftcan generate the Fokker100, the A380, the B737, etc…which are all different objects, all of type **Aircraft Instance-frames** are used to define **specific instances (objects)** of a generic class. E.g. Fokker100 is just one of the many possible instances of the generic class frame Aircraft 

Instance-frames are generated by assigning a set of specific values to the attributes of a class-frame. Any given set of attribute values yields a different, specific and unique instance-frame of the same class-frame.

## **The Unified Modeling Language (UML)** 

The UML is a standardized **visual language** used to model, design, and document software systems 

Emerged in the mid-1990s in response to the growing complexity of objectoriented software development and corresponding flourishing of several competing modeling methods 

- UML is a toolbox of diagram types, generally divided into 2 categories: 1. Structural diagrams, e.g. **class diagrams** , to describe the static architecture of a system 

2. Behavioral diagram, e.g. **activity diagrams** , to describe how the system behaves

## **To summarize…** 

- Frame Based Systems offer a more advanced domain knowledge representation than rule-based systems, featuring concepts from the **Objected Oriented modeling paradigm** 

- The concepts of **class-frame** allows defining few conceptual templates which can be reused (instantiated) to model many individual **instance-frames** 

- Frames can be connected* to other frames by means of **inheritance** and **composition/aggregation** links, thereby allowing complex-yet-efficient domain knowledge representations 

- The UML ( **Unified Modeling Language** ), an industry-standard visual language specifically developed to support OO modeling, offers very effective diagrammatic representation of systems, their components and relationships

## **…and to anticipate** 

- Frame slots can contain **pointers to slots of other frames** 

- Frame slots can contain **procedures (methods)** to dynamically compute their values 

- These procedures may include **IF-THEN** statements, as seen in ruled based KBSs* 

- The evaluation of these procedures can be **eager** or **on-demand** ( **lazy)** 

- Blurred separation between knowledge base and inference mechanism

## **Caching and dependency tracking** 

A dependency graph can be extremely large, concatenating thousands of function evaluations. 

. Suppose an attribute has already been computed If we (or some other element in the dependency graph) request its value again, should the system recompute it every time? 

- KBE systems provide a mechanism called **caching** which gives the ability to memorize (i.e. to cache) the value of computed attributes, so that they can be directly retrieved from memory, **if none of its dependencies have changed** 

- The **dependency tracking** mechanism keeps track of the current validity of the cached values. If dependencies have changed, it invalidate them*

## **KBE systems and link to CAD geometry kernels** 

- A **geometry kernel** is the computational engine running underneath a CAD system. 

   - It consists of a **collection of numerical algorithms and libraries** used to create and manipulate **curves, surfaces, and solid models** . 

   - It performs the actual geometric computations, such as intersections, Boolean operations, offsets, fillets, and so on. 

- KBE systems allow engineers to control these operations **programmatically** , which enables automated generation of complex parametric geometries.

## **KBE systems and link to CAD geometry kernels** 

- Many general-purpose languages can be used to integrate and control an external geometry kernel **through an API** 

- However, the way a KBE system interacts with a geometry kernel is distinctive: geometry is generated through a **declarative and functional model** , where geometric operations are **automatically** managed through **dependency tracking, caching, and lazy evaluation** 

- **ParaPy** uses the industry grade open source geometry kernel **Open Cascade**

## **UML extension for KBE - recap** 

- **Extends standard UML class diagrams** with stereotypes tailored to KBE (e.g., `<<inputs>>, <<@inputs>>, <<@attributes>>` ) to reflect ParaPy class elements 

- **Shows both class structure and generated object structure in one diagram** by naming instances on composition connectors (e.g., `fuselage : Cylinder` ) 

- **Captures dependency relations between components** using labeled dependency connectors (e.g., get position, get attribute X), while omitting implied parent→child dependencies to reduce clutter 

- **Represents runtime type selection** ( `DynamicType` ) by modeling alternative classes and constraining them so that only one class is instantiated (e.g., via {or} node or multiplicity constraint) 

- **Maintains UML compatibility** by using stereotypes, constraints, multiplicities, and associations, effectively functioning as a custom UML profile for KBE.

## **UML extension for KBE – why useful** 

- **Bridges the gap between UML and KBE frameworks (e.g., ParaPy)** by explicitly modeling object trees, dependencies, and configuration logic in a single diagram 

- **Improves readability of complex generative models,** avoiding multiple separate UML diagrams (class, object, dependency) 

- **Highlights essential knowledge dependencies and configuration choices,** making model behavior easier to understand, debug, and communicate 

- **Supports documentation of KBE systems,** helping engineers grasp how inputs, rules, and parts interact to generate engineering models

## **KBE application lifecycle:** _**[Capture&Formalize]**_ 

This phase includes two main activities: 

**==> picture [274 x 167] intentionally omitted <==**

**----- Start of picture text -----**<br>
PROBLEM or<br>OPPORTUNITY<br>IDENTIFICATION<br>KNOWLEDGE<br>CAPTURE  &<br>FORMALIZATION<br>**----- End of picture text -----**<br>


- **K. Capture** : engineering knowledge is extracted from the identified sources and structured through informalrepresentations based on natural language (e.g. diagrams, sketches, illustrations, text..)*. 

• **K. Formalization** : the captured knowledge is - refined and reshaped into formal yet programming language neutral – representations suitable to initiate code development (e.g. UML diagrams and algorithms pseudo-code)**. 

No coding on the KBE platform has actually started in this phase.
